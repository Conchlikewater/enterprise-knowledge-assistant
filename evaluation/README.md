# RAG V1 Offline Evaluation

This directory contains a synthetic, reproducible evaluation for the complete
local RAG pipeline. It requires no API key and sends no data to an external
provider.

## Corpus

The tracked corpus contains:

- 10 synthetic policy documents
- 6 UTF-8 TXT files
- 4 text-based PDFs
- 2 multi-page PDFs

`corpus_sources.json` is the canonical source. The files in `documents/` are
generated by `scripts/build_evaluation_corpus.py`.

## Questions

`questions.json` contains exactly 50 questions:

- 14 direct-answer questions
- 6 questions requiring multiple chunks
- 4 document-scope isolation questions
- 8 clearly unanswerable questions
- 6 paraphrased questions
- 6 similar-fact distractor questions
- 4 low lexical-overlap questions
- 2 deliberately ambiguous questions

Direct and multi-chunk questions search the full corpus, so Top-5 source
accuracy measures ranking quality rather than relying on a single-document
filter. Scope-isolation questions deliberately restrict the selected corpus.

Each question is also a typed ground-truth contract containing:

- `answerable`: whether the selected document scope contains an answer
- `expected_behavior`: `answer`, `refuse`, or `clarify`
- `expected_answer`: a concise reference answer, or `null` when unanswerable
- `expected_evidence`: exact source filename, page number, and source snippet

Exact evidence is stable across re-chunking experiments, unlike generated
chunk IDs. The loader rejects missing fields, contradictory answerability,
out-of-scope sources, invalid pages, and snippets that do not occur verbatim in
the canonical corpus.

`evaluation/metrics.py` provides dependency-free Hit Rate@K, Recall@K, and MRR
implementations. Hit Rate@K asks whether any relevant evidence was found,
Recall@K measures how much of all expected evidence was found, and MRR rewards
placing the first relevant result near the top. The evaluator matches evidence
only when the filename and page agree and the normalized chunk text contains
the exact annotated snippet.

The report includes the complete offline profile: provider names, embedding
dimensions, chunk size and overlap, Top-K, and score-threshold policy. Every
answerable question records its evidence Hit@5, Recall@5, reciprocal rank, and
the evidence numbers matched by each ranked result. This makes a failed metric
traceable to a particular query and chunk rank.

The report also groups results by question category. The harder categories are
intended to expose weaknesses that the original 20 straightforward questions
could hide; a non-perfect per-category score is a diagnostic signal, not a
claim that production accuracy has been measured.

## Offline provider

The evaluator uses a deterministic hashing-based lexical embedding provider.
It exercises the production parsing, chunking, SQLite, Qdrant, retrieval,
answer, citation, and deletion code without cloud cost. It is not intended to
estimate the semantic quality of the configured OpenAI model.

The unanswerable threshold of `0.25` was selected after recording the initial
bad case at `0.2289`. This threshold applies only to the offline evaluator and
does not silently change production retrieval behavior.

## Quality gates

The evaluation fails unless all of these conditions hold:

- all 10 documents ingest and produce non-empty chunks
- expected source filenames appear in Top-5 for at least 80% of answerable
  questions (a legacy source-level gate, not evidence Recall@K)
- evidence Hit Rate@5 and mean Recall@5 are each at least 80%
- evidence MRR is at least 0.75
- all six multi-chunk questions retrieve at least two expected chunks
- all four scope-isolation questions return no out-of-scope result
- at least 85% of questions marked `refuse` return no evidence or citations
- every citation maps to an actual retrieved chunk
- expected PDF page metadata is present
- deleting a document removes its file, record, and vectors

Run the evaluation from the project directory:

```powershell
.\.venv\Scripts\python.exe scripts\run_evaluation.py
```

The latest verified machine-readable result is stored in
`evaluation/latest_report.json`.

## Current expanded baseline

The tracked 50-question hashing baseline records:

- Top-5 source accuracy: 90.00%
- evidence Hit Rate@5: 82.50%
- evidence Recall@5: 82.50%
- evidence MRR: 0.7937
- unanswerable rejection rate: 87.50%
- clarification-candidate Recall@5: 100.00%
- clarification response rate: 0.00% (the API behavior is not implemented yet)
- 10 structured bad cases, including both planned clarification cases

Direct, multi-chunk, scope-isolation, and similar-fact distractor questions are
stable in this baseline. Paraphrases reach 50% evidence recall, while the four
low lexical-overlap questions miss their evidence. This is expected evidence
that the hashing provider cannot substitute for a semantic embedding model; it
defines the cases that later retrieval experiments must improve.

## Parameter experiments

`scripts/run_evaluation_experiments.py` executes five profiles. Every call to
the evaluator creates a fresh temporary SQLite database, upload directory, and
Qdrant collection, so vectors from different chunk configurations never mix.

| Profile | Chunk / overlap | Top-K | Recall@K | MRR | Bad cases |
|---|---:|---:|---:|---:|---:|
| baseline | 220 / 30 | 5 | 82.50% | 0.7937 | 10 |
| small chunks | 160 / 30 | 5 | 80.00% | 0.8000 | 11 |
| large chunks | 320 / 50 | 5 | 85.00% | 0.8187 | 8 |
| smaller result set | 220 / 30 | 3 | 80.00% | 0.7875 | 11 |
| larger result set | 220 / 30 | 10 | 87.50% | 0.7997 | 8 |

The `320 / 50 / Top-5` profile gives the best balance in this hashing-based
experiment, while Top-10 retrieves the most evidence at the cost of more
context. These results guide later semantic-embedding experiments; they do not
by themselves justify changing production defaults.

Run the comparison without network access:

```powershell

```

## Optional semantic embedding comparison

The offline hashing provider is intentionally lexical. To measure whether a real
semantic embedding improves paraphrases and low lexical-overlap questions, run
the opt-in comparison below after configuring `OPENAI_API_KEY` in `.env`:

```powershell
.\.venv\Scripts\python.exe scripts\run_semantic_evaluation.py --confirm-online
```

This command sends only the tracked synthetic corpus and its synthetic questions
to the configured OpenAI embedding model. It does not call an LLM for answer
generation, does not read production uploads, and uses fresh temporary SQLite
and Qdrant stores. Exact duplicate inputs are cached to reduce requests. The
explicit flag prevents accidental network use; the resulting comparison is
written to `evaluation/semantic_report.json`.

### Current semantic comparison

The tracked OpenAI `text-embedding-3-small` run uses the same `220 / 30 /
Top-5` retrieval profile as the hashing baseline:

| Metric | Hashing baseline | Semantic embedding | Delta |
|---|---:|---:|---:|
| Source Hit Rate@5 | 90.00% | 100.00% | +10.00 pp |
| Evidence Recall@5 | 82.50% | 100.00% | +17.50 pp |
| MRR | 0.7937 | 0.9833 | +0.1896 |
| Unanswerable rejection | 87.50% | 50.00% | -37.50 pp |
| Structured bad cases | 10 | 6 | -4 |

Semantic embeddings recover every paraphrase and low lexical-overlap evidence
case in this synthetic set. However, the hashing baseline's `0.25` refusal
threshold is not calibrated for OpenAI cosine scores, so four unanswerable
questions incorrectly retain evidence. The two ambiguous cases retrieve all
candidate evidence but still fail because the API does not yet return a
clarification response. These results justify a threshold experiment; they do
not justify changing production defaults yet.

### Refusal-threshold sweep

The semantic report also replays the recorded Top-5 scores across thresholds
without making additional API calls. On this 50-question synthetic set:

- `0.37` through `0.41` form a stable perfect interval: evidence recall 100%,
  unanswerable rejection 100%, and answerable false refusal 0%.
- `0.36` still accepts one unsupported question, leaving rejection at 87.50%.
- `0.42` creates the first false refusal and lowers evidence recall to 97.50%.

The script reports `0.37`, the lowest threshold in the best interval, as the
dataset candidate. This preserves the largest margin for answerable evidence,
but it remains an experimental result rather than a production default. A larger
and more representative corpus is required before deployment.

## Hybrid retrieval prototype

`evaluation/hybrid.py` contains two dependency-light experimental components:

- an in-memory BM25 retriever for identifiers, exact terms, and lexical matches;
- reciprocal rank fusion (RRF), which combines rankings without treating BM25
  and cosine scores as if they shared one numeric scale.

Both components enforce document scope and deterministic ordering. The
evaluation runner records the exact chunks written to Qdrant, so BM25 and dense
retrieval rank the same chunk IDs rather than separately re-chunked copies. RRF
combines ranks, not raw BM25 and cosine scores.

Run the dependency-free comparison with:

```powershell
.\.venv\Scripts\python.exe scripts\run_hybrid_evaluation.py
```

The current 50-question hashing comparison records:

| Metric | Dense hashing | Dense + BM25/RRF | Delta |
|---|---:|---:|---:|
| Evidence Recall@5 | 82.50% | 82.50% | 0.00 pp |
| MRR | 0.7937 | 0.8000 | +0.0063 |
| Answerable retrieval bad cases | 7 | 7 | 0 |

This result does not justify a production change. It only moves the first
relevant result slightly upward on average; it finds no additional evidence and
fixes no retrieval bad case. The hashing provider and BM25 are both mainly
lexical, so their strengths overlap. The exploratory normalized RRF threshold
sweep also cannot meet the refusal gate without rejecting too many answerable
questions: its best candidate rejects 75% of unsupported questions but falsely
refuses 25% of answerable questions. The tracked report therefore sets
`production_change_recommended` to `false`.

The production API still uses dense Qdrant retrieval. A fair Hybrid decision
requires the same experiment with the real semantic provider; even then, the
retrieval and refusal metrics must be considered together.

### Semantic Hybrid decision

The opt-in semantic comparison uses OpenAI `text-embedding-3-small` for both
arms, with identical `220 / 30 / Top-5` settings and identical ingested chunks:

| Metric | Semantic Dense | Semantic Dense + BM25/RRF | Delta |
|---|---:|---:|---:|
| Evidence Recall@5 | 100.00% | 92.50% | -7.50 pp |
| MRR | 0.9833 | 0.8438 | -0.1395 |
| Answerable retrieval bad cases | 0 | 3 | +3 |

Equal RRF fusion introduces three regressions: `paraphrase-05`, `low-score-03`,
and `low-score-04`. In each case the semantic dense retriever had recovered the
evidence, but BM25's lexical ranking gave unrelated or incomplete chunks enough
rank weight to push the exact evidence outside Top-5. This is a useful negative
result: Hybrid retrieval is not automatically better, and equal fusion weights
are not justified by architecture alone.

The Hybrid normalized-score sweep also fails the acceptance boundary. Its best
candidate (`0.98`) retains 82.50% evidence recall, rejects 87.50% of unsupported
questions, and falsely refuses 7.50% of answerable questions. The tracked report
therefore rejects a production change and keeps semantic Dense as the current
retrieval strategy.

Run this comparison only after explicitly accepting the external request and
cost:

```powershell
.\.venv\Scripts\python.exe scripts\run_semantic_hybrid_evaluation.py --confirm-online
```

Only the tracked synthetic corpus and questions are sent to the embedding API;
the experiment does not call an LLM or access production uploads. The result is
stored in `evaluation/semantic_hybrid_report.json`.

## Bad-case catalogue

`evaluation/bad_case_report.json` converts completed experiment failures into
five traceable groups rather than one undifferentiated accuracy number:

| Group | Failure stage | Count | Decision/status |
|---|---|---:|---|
| Hashing answerable misses | retrieval | 7 | baseline limitation |
| Hashing false acceptance | refusal threshold | 1 | baseline limitation |
| Semantic false acceptance at `0.25` | refusal threshold | 4 | synthetic candidate found, not promoted |
| Ambiguous questions | response policy | 2 | clarification planned |
| Semantic Hybrid regressions | retrieval ranking | 3 | experiment rejected |

The catalogue records the current decisions explicitly: use semantic Dense,
do not promote the equal-weight Hybrid experiment, do not silently change the
production threshold, and keep clarification behavior as a visible product gap.
It is rebuilt without network calls from the tracked evaluation reports:

```powershell
.\.venv\Scripts\python.exe scripts\build_bad_case_report.py
```

## Local latency benchmark

`scripts/run_latency_benchmark.py` runs three fresh offline evaluation rounds.
Each round uses five warmup questions and measures the remaining 45, producing
135 samples in total. The current machine records:

| Local measurement | P50 | P95 |
|---|---:|---:|
| Retrieval only | 7.6400 ms | 7.9261 ms |
| Answer orchestration | 7.6006 ms | 7.9745 ms |

The observer measures one explicit retrieval call and then the complete answer
service call, which performs its own retrieval. Timing is stored separately from
the deterministic quality report so normal machine variance does not create a
false quality-report diff.

These are local engineering measurements, not production latency claims. The
benchmark uses hashing embeddings, temporary local Qdrant and SQLite stores,
the deterministic evaluation LLM, and a small synthetic corpus. It excludes
OpenAI network latency, real concurrency, large documents, and server load.

Run it without an API key:

```powershell
.\.venv\Scripts\python.exe scripts\run_latency_benchmark.py
```

The latest measurement and its limitations are stored in
`evaluation/latency_report.json`.
