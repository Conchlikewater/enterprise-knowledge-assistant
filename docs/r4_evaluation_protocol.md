# R4 同步 / 异步摄取评测协议

> 状态：2026-09-05 预注册；本文件先于基准实现和结果提交。这里冻结测量方法，不预设结果方向。

## 1. 目标与边界

R4 回答一个具体工程问题：在当前单机、小规模文档和单 Worker 边界内，R23 的异步摄取是否值得作为作品集演示的首选路径？

结论只允许影响演示和文档措辞：

- 保留 `POST /api/v1/documents -> 201`，不破坏同步兼容接口；
- 保留 `POST /api/v2/documents -> 202 + job_id`；
- 不在 R4 新增任务功能、重试、取消、多 Worker 或 Agent；
- 不把本机基准写成生产吞吐或真实 Provider 性能；
- 不调用 OpenAI、DeepSeek 或其他付费 Provider。

## 2. 固定实验条件

正式报告必须记录实际机器、操作系统、Python 和 Qdrant 版本。两条路径共享以下条件：

| 项目 | 冻结值 |
| --- | --- |
| 文档 | 每组字节对应一致、内容唯一的 8 KiB 合成 TXT |
| Chunk | `chunk_size=1000`、`chunk_overlap=150` |
| Embedding | 3 维确定性 Provider，每次文档批次固定等待 200 ms |
| Vector store | 同一个 Qdrant Server，使用隔离的临时 collection |
| Metadata | 使用隔离的临时 SQLite 和上传目录 |
| HTTP | FastAPI + `httpx.ASGITransport`，测应用层请求，不含公网和 Uvicorn socket 开销 |
| Worker | 与 API 分离的 Python 子进程，单 Worker |
| 预热 | 每条路径 2 份文档，不计入样本 |
| 单文档样本 | 每条路径 20 份，奇偶轮交替先测同步或异步 |
| 连续上传 | 3 轮，每轮顺序提交 5 份文档，轮次交替执行顺序 |
| 健康探针 | 每条路径处理长任务期间各 5 次 `/health` 请求 |
| 异步轮询 | 10 ms，端到端时间包含客户端观察到 ready 的轮询开销 |
| 请求预算 | 100 ms；只判断是否暴露于该客户端等待预算，不声称普适超时阈值 |
| 崩溃恢复 | 固定执行 1 次“Qdrant upsert 后、SQLite ready 前”进程退出与恢复 |

固定 200 ms 延迟用于把“长耗时摄取”从机器噪声中分离出来，不表示任何线上模型的真实延迟。正式报告必须同时保留这一限制。

## 3. 七项测量定义

### 3.1 API 接收延迟

- 同步：从发出 V1 POST 到收到 `201`；响应时 Document 已 ready。
- 异步：从发出 V2 POST 到收到 `202`；响应时 Job 为 pending 或已经被 Worker 领取。
- 分别记录原始样本、mean、P50、P95、min 和 max。

### 3.2 端到端完成时间

- 同步：与该请求的接收延迟相同。
- 异步：从发出 POST 到通过 Job GET 首次观察到 ready。
- 端到端更快不是异步成立的必要条件，必须如实报告排队和轮询成本。

### 3.3 上传期间 API responsiveness

在确定性 Provider 已进入 200 ms 等待区间时请求 `/health`，记录 5 次探针延迟和状态码。该指标检查 API 是否还能响应，不把一次本地探针解释为高并发容量。

### 3.4 连续上传

客户端顺序发送 5 次上传，记录：

- 每次响应延迟的 P50/P95；
- 收到全部上传响应所需时间；
- 全部文档达到 ready 的时间。

顺序上传刻画“上一个请求返回后再发下一个”的普通脚本或人工演示行为；不把它冒充并发压测。

### 3.5 崩溃恢复

异步路径在固定崩溃点以退出码 91 结束。随后启动新的 Worker，记录：

- 是否恢复同一 Job；
- 恢复耗时；
- 最终 Job/Document 状态；
- `attempt_count` 是否为 2；
- 可见 Chunk 数是否与 Document 一致且 `chunk_id` 无重复。

同步路径没有持久化 Job 或独立 Worker，因此该能力记为“不适用/不支持”，不能伪造对称数字。

### 3.6 长任务请求预算

比较 API 接收延迟 P95 与预注册的 100 ms 客户端等待预算：

- `p95 > 100 ms` 记为暴露于该预算；
- `p95 <= 100 ms` 记为未暴露；
- 不主动取消请求，避免把客户端取消副作用混入摄取测量；
- 该判断只适用于本协议的 200 ms 受控工作负载。

### 3.7 复杂度差异

不使用主观的“代码很多/很少”，固定记录以下架构计数和责任：

| 维度 | 同步 V1 | 异步 V2 |
| --- | ---: | ---: |
| 运行服务 | API + Qdrant（2） | API + Worker + Qdrant（3） |
| 持久化生命周期对象 | Document（1） | Document + Job（2） |
| 完成状态 HTTP 交互 | POST 响应（1 类） | POST + Job GET（2 类） |
| 恢复责任 | 请求失败补偿 | 原子领取、启动恢复、重放清理、状态查询 |

同时说明 SQLite 双进程、Worker 运维和轮询带来的新增故障面。

## 4. 公平性与污染控制

- 对应样本使用相同字节、文件大小和参数；不同模式使用隔离数据库与 collection，避免 SHA 唯一约束冲突。
- 单文档样本按奇偶轮交替先后顺序；连续上传的三轮也交替顺序，降低固定先测一方的热缓存偏差。
- 正式计时前完成预热；清理、启动和报告序列化时间不计入请求延迟。
- 所有成功响应必须核对状态码，所有异步样本必须最终观察到 ready；任何 failed、超时或样本数不一致都使正式运行失败。
- 报告保存原始样本和聚合值；测试只校验契约和逻辑关系，不冻结具体毫秒值。
- 崩溃恢复使用真实 Qdrant Server 和真实独立 Python 进程，但仍使用确定性 Embedding。

## 5. 预注册判断规则

只有同时满足以下条件，报告才可建议“V2 作为长耗时摄取的演示首选路径，V1 保留兼容”：

1. 异步 API 接收 P95 低于同步 P95；
2. 在本协议中，异步接收 P95 不超过 100 ms，而同步接收 P95 超过 100 ms；
3. 连续 5 次上传时，异步收到全部响应的时间低于同步；
4. 固定崩溃恢复成功，最终无重复可见 Chunk；
5. 完整质量门禁和 Qdrant Server 集成测试通过。

若 1–4 任一项不满足，结论保持“两条路径并存，不提升异步为演示首选”；若崩溃恢复失败，R4 直接失败并回到 R23 修复。端到端时间无论快慢都必须展示，不能因不利而删除。

“演示首选”不等于生产替换、高并发验证或公网部署建议。

## 6. 交付与 Git 时序

提交顺序固定为：

1. 本协议与 R4 开工状态；
2. 基准实现和自动化测试；
3. 机器生成 JSON、分析报告、README/DEV_STATE 结论。

协议提交后才能运行正式基准。结果提交不得修改本协议中的样本数、阈值或判断规则；如果环境导致协议无法执行，必须停止并单独记录偏差，不能静默改口径。

## 7. 验收与限制

R4 完成需要：

- 七项都有数据或明确的“不支持”说明；
- 结果可以用同一命令重跑；
- 自动化测试覆盖统计、判断函数、报告 Schema 和短配置的 Server 集成冒烟；
- 完整质量门禁通过且不调用真实 Provider；
- README、结果报告和 DEV_STATE 使用同一结论；
- ⑤拥有权验证保持未完成，阶段停止等待用户问答。

本评测不覆盖真实模型网络延迟、大文件、并发压测、多个 Worker、跨机器、网络分区或生产容量。
