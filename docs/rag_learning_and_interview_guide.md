## 2. 一句话理解项目

RAG 的核心是：**先从用户选择的资料中检索证据，再让大模型只根据证据组织答案，并返回可核查的引用；证据不足时拒答。**

本项目不是训练了一个新的“RAG 模型”，而是组合 FastAPI、SQLite、Qdrant、OpenAI Embedding 和 LLM 构建了一个 RAG 应用。

## 3. 两条必须记住的完整链路

### 3.1 文档上传链路

```text
TXT/PDF 上传
  → FastAPI 接收文件
  → 文件类型、大小、空文件等校验
  → 原文件保存到 data/uploads
  → 解析文字
  → 切分为 Chunk
  → OpenAI Embedding 生成1536维向量
  → Chunk、向量和来源信息写入 Qdrant
  → 文档元数据和状态写入/更新 SQLite
  → PROCESSING 变为 READY
```

处理中发生异常时：清理不完整文件和向量，将已创建的文档记录更新为 `FAILED`，避免不同存储之间的数据不一致。

### 3.2 用户提问链路

```text
用户问题文字
  → FastAPI 接收 question、document_ids、top_k 等参数
  → 检查所选文档存在且状态为 READY
  → Embedding 将问题转换成向量
  → Qdrant 比较问题向量和 Chunk 向量
  → 只在指定 document_ids 中返回相关 Chunk 原文
  → 根据 top_k 和 score_threshold 排序过滤
  → AnswerService 将“问题文字 + Chunk 原文”交给 LLM
  → 应用层根据真实检索结果构造结构化引用
  → 返回 answer、citations、retrieval_count
```

必须牢记：**向量交给 Qdrant 用于检索；大模型阅读的是问题文字和 Chunk 原文，不是向量。**

## 4. 组件、名词和用途

| 名词 | 简单解释 | 在本项目中的用途 |
|---|---|---|
| RAG | 检索增强生成 | 先检索企业资料，再基于证据生成答案 |
| Document | 一份完整上传文件 | TXT 或文本型 PDF，拥有唯一 `document_id` |
| Chunk | 文档切分后的小段文本 | 检索和引用的基本单位，拥有唯一 `chunk_id` |
| Chunk size | 单个 Chunk 的目标长度 | 默认1000；影响上下文完整度、检索精度和成本 |
| Chunk overlap | 相邻 Chunk 重叠部分 | 默认150；减少信息被切分边界截断的风险 |
| Embedding | 将文本映射为向量 | `text-embedding-3-small` 生成1536维向量 |
| Vector | 表示文本语义的一组数字 | 用于计算问题与 Chunk 的语义相似度 |
| Cosine similarity | 比较两个向量方向的相似度 | Qdrant 用它排序相关 Chunk；分数不是答案正确率 |
| SQLite | 轻量关系型数据库 | 保存文档元数据、处理状态、Chunk 数量和时间等 |
| Qdrant | 向量数据库 | 保存 Chunk、向量和来源信息，执行文档范围语义检索 |
| `data/uploads` | 本地上传目录 | 保存原始 TXT/PDF 文件；SQLite 不保存正文全文 |
| Metadata | 描述数据的数据 | 文件名、类型、大小、状态、页码、ID、时间等 |
| LLM | 大语言模型 | 阅读问题和检索证据，组织最终自然语言答案 |
| Hallucination | 模型生成无证据或错误内容 | 通过范围检索、证据提示、引用和拒答降低风险 |
| Citation | 答案来源 | 包含文档 ID、Chunk ID、文件名、摘录、页码和分数 |
| Document scope | 文档搜索范围 | 检索只允许返回用户选择的 `document_ids` |
| `top_k` | 最多保留的检索结果数 | `top_k=3` 表示最多3条，不保证一定返回3条 |
| `score_threshold` | 最低相似度阈值 | 低于阈值的 Chunk 被过滤；需要通过评估校准 |
| `retrieval_count` | 实际采用的检索结果数 | 帮助判断回答用了多少条证据 |
| FastAPI | Python Web API 框架 | 接收请求、校验数据、调用 Service、返回 JSON 和状态码 |
| Router | 接口入口和路由规则 | 规定请求方法、路径，以及调用哪个函数 |
| Schema | 输入/输出数据格式 | Pydantic 模型校验字段并生成 OpenAPI 文档 |
| Service | 业务流程协调层 | 组织摄取、检索、回答、删除等完整业务流程 |
| Repository | 数据仓库接口 | 屏蔽 SQLite 的具体实现，提供文档增删查改能力 |
| Provider | 外部能力适配接口 | 屏蔽 OpenAI 等模型提供方的具体调用方式 |
| Dependency | FastAPI 依赖 | 将已经准备好的 Service 提供给 Router |
| OpenAPI | 机器可读的接口说明标准 | FastAPI 在 `/openapi.json` 自动生成接口定义 |
| Swagger UI | 浏览器接口测试页面 | FastAPI 在 `/docs` 自动生成，供开发和调试使用 |
| UUID | 唯一标识符 | 用于生成 `document_id`、`chunk_id` 和 `request_id` |
| SHA-256 | 文件内容指纹 | 识别文件内容并支持重复/完整性检查，不是加密正文 |
| Rollback | 失败后的补偿清理 | 删除不完整向量和文件，更新失败状态 |
| Request ID | 单次请求的追踪编号 | 在错误响应和日志间定位同一次请求，不记录隐私正文 |

## 5. 数据到底保存在哪里

| 数据 | 保存位置 |
|---|---|
| 原始 TXT/PDF | `data/uploads` |
| 文档 ID、文件名、类型、大小、SHA-256、状态、Chunk 数量、时间 | SQLite |
| Chunk 原文、Chunk 向量、文档 ID、Chunk ID、文件名、页码 | Qdrant |
| API Key | 本地 `.env`，被 Git 忽略，不能提交或打印到日志 |

常见错误说法：

- 错：SQLite 保存文档全文。对：SQLite 主要保存文档元数据和状态。
- 错：Embedding 使用余弦算法生成向量。对：Embedding 生成向量，Qdrant 使用余弦相似度比较向量。
- 错：大模型接收向量。对：Qdrant 接收向量，大模型接收问题和 Chunk 原文。
- 错：相似度0.70表示答案有70%概率正确。对：它只表示两个向量的相似程度。
- 错：`top_k=3` 一定返回3条。对：它表示最多返回3条。
- 错：没有答案说明程序出错。对：文档没有足够证据时应当拒答。

## 7. 文档状态

```text
PROCESSING → READY
          ↘ FAILED
```

- `PROCESSING`：记录已创建，摄取尚未完成。
- `READY`：文件解析、Chunk、Embedding和Qdrant写入全部完成，可以检索。
- `FAILED`：处理中发生异常，不能参与检索。

状态的意义不是美化页面，而是防止对未完成或失败的文档执行检索。

## 8. `/search` 与 `/answers` 为什么同时保留

- `/search` 只检查检索质量，返回 Chunk 原文、来源和分数，不调用 LLM。
- `/answers` 提供端到端问答，先复用检索，再调用 LLM 并返回引用。
- 拆分后可以判断问题发生在检索阶段还是生成阶段。
- 只需要证据的调用方可使用 `/search`，降低成本和延迟。

## 9. 引用和拒答是怎么实现的

### 9.1 结构化引用

LLM 按提示在答案文字中使用 `[1]` 等来源编号。应用程序再根据真实检索结果构造结构化 `citations`：

- `citation_number`
- `document_id`
- `chunk_id`
- `filename`
- `page_number`
- `excerpt`
- `score`

结构化来源信息不是让 LLM 自由编写，因此比只让模型输出一个文件名更可靠。

### 9.2 两层无证据处理

1. 检索没有结果：应用程序直接返回固定拒答，不调用 LLM。
2. 检索有结果但证据不支持问题：LLM 被要求返回固定的“证据不足”标记，应用程序再转换成统一拒答。

拒答不能彻底消除幻觉，但可以明显降低没有证据时强行回答的风险。

## 12. 1分钟项目介绍

我做了一个面向企业知识问答的 RAG 应用。它的目标是让用户上传 TXT 或 PDF 文档后，系统能够基于用户选择的文档回答问题、提供来源引用，并在文档证据不足时拒绝回答。

项目后端使用 FastAPI 构建。文档上传后，系统会依次完成文件校验、文本解析和 Chunk 切分，再通过 OpenAI Embedding 模型生成向量。SQLite 负责管理文档 ID、文件名、处理状态和 Chunk 数量等信息，Qdrant 负责保存 Chunk 及其向量。

用户提问时，系统先把问题转换成向量，在指定文档范围内检索相关 Chunk，再把问题和检索到的 Chunk 原文交给大模型生成答案。结构化引用由应用程序根据真实检索结果构造，从而降低答案和来源编造的风险。

目前项目已经实现 TXT/PDF 摄取、文档范围检索、证据回答、结构化引用、无证据拒答和统一错误处理，并通过自动化测试和离线评估验证了主要流程。

记忆顺序：**目标 → 上传 → 提问 → 保护机制和验证。**

## 13. 3分钟项目介绍

我做了一个面向企业内部知识问答的 RAG 应用。这个项目主要解决两个问题：第一，通用大模型不了解企业内部文档；第二，直接让模型回答容易出现答案或来源编造。因此，我希望系统能够先从用户指定的文档中寻找证据，再让大模型根据证据回答，并返回可以核查的引用。

V1采用 FastAPI 模块化单体架构。选择模块化单体，是因为当前项目规模还不需要微服务，但仍然需要把接口、业务服务、文档处理、模型提供方和存储层分开，便于测试和后续扩展。SQLite 用于管理文档 ID、文件名、状态和 Chunk 数量等元数据；Qdrant 用于保存 Chunk、向量和来源信息；OpenAI 提供 Embedding 和大模型生成能力。

文档上传后，FastAPI Router 将任务交给 IngestionService。Service 首先检查文件类型、大小和内容，然后保存文件并在 SQLite 中创建 processing 状态的记录。接下来读取 TXT 或文本型 PDF，将内容切分成带少量重叠的 Chunk，再调用 Embedding 模型生成1536维向量，并把 Chunk 和向量写入 Qdrant。全部成功后文档状态更新为 ready；如果中途失败，系统会删除不完整的文件和向量，并把记录更新为 failed，避免不同存储之间的数据不一致。

用户提问时，RetrievalService 先检查所选文档是否存在并处于 ready 状态，然后把问题转换成向量，只在用户指定的 document_ids 范围内进行语义检索。Qdrant 使用向量相似度返回相关 Chunk，系统再根据 top_k 和 score threshold 排序过滤。

AnswerService 得到检索结果后，把问题和 Chunk 原文交给大模型生成答案。向量只用于检索，不会直接交给大模型。如果没有满足条件的证据，系统直接拒答；如果有证据，则由应用程序根据真实检索结果构造 document_id、chunk_id、文件名、原文摘录和相似度等结构化引用，降低来源编造风险。

目前项目已经实现 TXT/PDF 同步摄取、文档范围检索、证据回答、结构化引用、无证据拒答、统一错误处理和隐私安全日志。项目当前有143项自动化测试通过和34个subtests，分支覆盖率为88.20%，并使用10份文档和50个问题建立了离线评估集。V2还比较了离线Hashing、真实语义Dense和Dense+BM25/RRF：真实语义Dense的Recall@5为100%、MRR为0.9833；等权Hybrid的Recall降至92.50%、MRR降至0.8438，所以没有把更复杂但效果更差的方案接入生产API。V1目前仍是同步处理，也没有认证、多租户和正式前端，这些是后续可以继续优化的方向。

记忆顺序：**目标 → 架构 → 上传 → 检索 → 回答 → 验证与不足。**

## 14. 基础问题与参考答案

### 1. 什么是 RAG？

RAG 是检索增强生成。系统先从外部知识库检索与问题相关的证据，再把证据和问题交给大模型生成答案。它的价值是让答案基于指定资料，并提供来源，而不是完全依赖模型参数中的通用知识。

### 2. 这个项目是训练了一个新模型吗？

没有。它是一个 RAG 应用，组合了文档处理、Embedding、Qdrant检索、LLM生成、引用和拒答等能力。V1调用现有OpenAI模型，没有微调或训练新的基础模型。

### 3. 上传文档后发生了什么？

系统检查文件类型、大小和内容，保存原文件，在SQLite创建processing记录，解析TXT/PDF，切分Chunk，调用Embedding生成向量，将Chunk和向量写入Qdrant，最后把文档状态更新为ready；异常时回滚并标记failed。

### 4. 用户提问后发生了什么？

系统验证问题和所选文档，把问题转换成向量，在指定document_ids内检索相关Chunk，按top_k和阈值过滤，再把问题和Chunk原文交给LLM生成答案，并由应用层构造结构化引用。

### 5. Document和Chunk有什么区别？

Document是一份完整上传文件；Chunk是从Document中切分的小段文本。Document用于管理生命周期，Chunk用于检索和引用。

### 6. 为什么需要切分？

整份文档可能太长且包含大量无关信息。切分后可以只检索与问题相关的小段，降低上下文成本并提高定位精度。切分过小会丢失上下文，过大会混入噪声，因此需要评估调整。

### 7. Embedding是什么？

Embedding把文本转换成高维向量，使语义接近的文本在向量空间中更接近。本项目使用`text-embedding-3-small`生成1536维向量。

### 8. 余弦相似度是什么？

它比较两个向量方向的接近程度。本项目用它衡量问题向量和Chunk向量的语义相似度。相似度分数用于排序检索结果，不等于答案正确概率。

### 9. SQLite和Qdrant分别保存什么？

SQLite保存文档元数据和处理状态；Qdrant保存Chunk原文、向量和来源信息并执行语义检索。原始文件保存在`data/uploads`。

### 10. FastAPI负责什么？

FastAPI提供HTTP接口，接收和校验请求，调用Service，返回JSON、状态码和统一错误响应，并根据Router和Schema自动生成OpenAPI/Swagger文档。

### 11. Router、Schema和Service有什么区别？

Router决定什么路径和请求方法调用哪个函数；Schema规定输入输出数据格式；Service组织真正的业务流程。这样分层可以减少接口代码复杂度并方便测试。

### 12. `/search`和`/answers`有什么区别？

`/search`只返回检索到的Chunk和分数，不调用LLM；`/answers`先检索，再调用LLM生成答案和引用。拆开后便于评估、调试和支持只需要原始证据的场景。

### 13. 大模型接收向量吗？

不接收。问题和Chunk先分别被Embedding转换为向量，Qdrant比较向量并返回相关Chunk原文；LLM最终接收的是问题文字和Chunk原文。

### 14. 如何限制文档搜索范围？

请求必须明确提供`document_ids`。RetrievalService先验证文档存在且ready，再将这些ID传给VectorStore作为过滤范围，并检查返回结果不能超出允许集合。

### 15. `top_k`是什么？

它表示最多保留多少个最相关检索结果。值太小可能漏证据，太大可能引入噪声、增加上下文长度和LLM成本。

### 16. `score_threshold`是什么？

它是最低相似度阈值。低于阈值的Chunk被过滤。阈值过低会引入无关证据，过高会误拒答，需要使用评估集校准。

### 17. 引用如何生成？

LLM按提示在答案中写`[1]`等编号；应用程序依据真实RetrievalResult构造citation对象，包括文件名、文档ID、Chunk ID、原文摘录、页码和分数，而不是让模型自由编写来源元数据。

### 18. 无证据拒答如何实现？

检索结果为空时，AnswerService直接返回固定拒答和空引用，不调用LLM；如果检索有结果但证据仍不支持问题，LLM被要求返回固定证据不足标记，应用再转换成统一拒答。

### 19. processing、ready、failed有什么用？

它们表示文档生命周期。只有ready文档可以检索。状态防止用户查询尚未处理完成或已经失败的文档，也方便排错和恢复。

### 20. 为什么需要回滚？

文档摄取同时涉及文件系统、SQLite、Embedding和Qdrant，其中一步失败可能留下部分数据。回滚会删除不完整文件和向量并更新失败状态，降低存储不一致风险。

### 21. Swagger页面是真网站吗？

它是真实运行的本地接口页面，但不是公网网站或正式前端。FastAPI根据OpenAPI定义自动生成`/docs`，只在本机服务运行时可用。

### 22. 为什么空文件返回400？

文件虽然满足上传请求格式，但内容违反业务规则，因此返回400和`EMPTY_FILE`。系统在Embedding前拒绝空文件，避免无意义调用和脏数据。

### 23. 为什么删除成功返回204且没有正文？

204表示请求成功但无需返回内容。删除结果可以再通过文档列表或按ID查询验证。

### 24. 为什么需要Request ID？

它把接口响应和日志中的同一次请求关联起来。出现错误时可以根据Request ID定位日志，同时避免在错误信息中暴露文档正文或API Key。

### 25. 你在项目中具体做了什么？

我参与确定了V1的功能范围和技术边界，包括FastAPI模块化单体、SQLite、Qdrant、文档范围检索和结构化引用。我持续检查功能结果，推进文档摄取、检索、回答、测试和文档整理，并使用AI编程工具辅助实现和调试。我的重点是需求取舍、验收标准、测试验证和问题修复，而不是把无法解释的生成代码直接当作成果。

离线评估使用可重复的哈希词汇Embedding替身，不调用OpenAI、不产生费用，也不用于估计真实OpenAI模型的语义质量。

### 1. Chunk太大或太小有什么影响？

太小容易割裂语义，需要检索更多Chunk才能回答；太大容易混入无关主题，使语义被稀释，降低检索精度并增加LLM输入成本。合理值取决于文档类型和问题，需要通过评估集调整。本项目V1默认`chunk_size=1000`。

### 2. 为什么需要Chunk overlap？

Overlap让相邻Chunk共享一部分文字，减少一句话、一个步骤或一组条件被切分边界截断的问题。Overlap过大则会产生重复结果，增加Embedding、存储和检索噪声。本项目V1默认`chunk_overlap=150`。

### 3. 为什么使用向量检索？

关键词检索依赖字面匹配，向量检索可以找到表达不同但语义相近的内容。例如“年假天数”和“一年能休几天”用词不同但语义接近。向量检索并不一定更简单，也可能在产品编号、专有名词、法规条款、精确金额等场景表现不足。

### 4. 为什么未来考虑BM25和reranker？

BM25擅长关键词、编号和精确词汇匹配，向量检索擅长语义匹配，二者可以组成混合检索。第一阶段召回候选结果后，reranker再使用更强的相关性模型重新排序，以提高最终证据质量。是否引入应由评估结果决定。

### 5. `top_k`和`score_threshold`如何影响结果？

`top_k`控制最多保留多少个Chunk；太小可能漏证据，太大会引入噪声并增加LLM成本。`score_threshold`控制最低相似度；太低会接受无关证据，太高会产生误拒答。演示使用`0.99`只是为了稳定触发无证据分支，不是生产推荐值。

### 6. 为什么使用FastAPI模块化单体？

V1规模较小，核心目标是先完成摄取、检索、回答、引用和拒答闭环。模块化单体部署和调试成本较低，同时仍通过Router、Service、Provider和Storage划分边界。微服务会增加服务通信、部署、监控和数据一致性复杂度，当前收益不足；未来规模扩大后可以沿已有模块边界拆分。

### 7. 143项测试和34个subtests说明什么？

测试覆盖配置、文件校验、TXT/PDF解析、Chunk切分、Repository、VectorStore、Provider适配、摄取、检索、回答、错误处理和API集成链路。它们不仅检查正常情况，也检查空文件、错误状态、Provider失败和回滚等边界场景。测试通过说明当前预设行为符合断言，但不代表项目没有未知Bug或已经达到生产级可靠性。

### 8. 覆盖率表怎么看？

| 列 | 含义 |
|---|---|
| `Stmts` | 可执行语句数量 |
| `Miss` | 没有被测试执行的语句数量 |
| `Branch` | `if/else`、异常等条件分支数量 |
| `BrPart` | 只执行了部分方向的分支数量 |
| `Cover` | 语句与分支综合覆盖率 |
| `Missing` | 未覆盖的具体代码行 |

`88.20%`表示大多数语句和分支被测试运行过，不是RAG答案正确率，也不代表断言一定设计得足够好。项目设置`fail_under=85`，以后改动导致覆盖率低于85%时质量检查会失败。

### 9. `25 files skipped due to complete coverage`是什么意思？

不是跳过25个测试，而是25个代码文件已经达到完整覆盖。由于配置了`skip_covered=true`，覆盖率表为了简洁没有展开这些文件。

### 10. 10份文档和50个问题如何设计？

语料包含6份TXT、4份PDF，其中2份为多页PDF。50个问题分为：

- 14个直接问题：通常由一个核心Chunk支持。
- 6个多Chunk问题：需要同时找回多个证据。
- 4个范围隔离问题：检查是否返回范围外内容。
- 8个不可回答问题：检查系统是否拒答。
- 6个改写问题：检查不同措辞下的语义召回。
- 6个相似事实干扰问题：检查是否被近似内容误导。
- 4个低词法重叠问题：暴露关键词方法的局限。
- 2个歧义问题：要求未来返回澄清或多个候选证据。

### 11. 各离线指标分别验证什么？

- `top5_source_accuracy`：预期来源是否进入前5个检索结果。
- `multi_chunk_pass_rate`：多Chunk问题是否找回至少两个必要证据。
- `scope_isolation_pass_rate`：是否没有返回所选文档范围之外的结果。
- `unanswerable_rejection_rate`：不可回答问题是否返回空证据和空引用。
- `citation_integrity_pass_rate`：每条引用是否对应真实检索Chunk。
- `pdf_page_metadata_pass_rate`：PDF来源是否保留预期页码。
- `deletion_passed`：删除后文件、SQLite记录和Qdrant向量是否都消失。

### 12. 为什么离线指标100%不能说项目真实准确率100%？

因为只有10份合成文档和50个预先设计的问题，问题和预期来源都是已知的；即使真实语义Dense在这50题上Recall@5达到100%，也没有覆盖扫描PDF、复杂表格、真实脏数据、高并发、网络波动和长期运行。准确说法是：当前合成集上的证据召回结果通过，不能外推为生产准确率100%。

### 13. 自动化测试与RAG离线评估有什么区别？

自动化测试主要验证“代码是否按设计工作”，例如空文件是否返回400、失败是否回滚；RAG评估主要验证“检索与证据行为是否符合预期”，例如正确来源是否进入Top-5、范围隔离和拒答是否生效。自动化测试防代码回归，RAG评估衡量当前语料上的工程效果，二者不能互相替代。

### 14. 一个真实问题排查案例是什么？

真实摄取联调时，上传后的文档状态变为`failed`，Chunk数量为0。先根据状态判断请求已经进入摄取流程但未完成向量写入，再按文件解析、Embedding、Qdrant和SQLite分层检查，并单独调用Embedding Provider。最终定位为运行环境禁止外部网络连接，而不是解析或Qdrant代码错误。获得网络权限后，先验证Embedding返回1536维向量，再回归验证上传状态`ready`、检索结果、带引用回答和无证据拒答。这个案例说明应根据状态和日志分层排查，也说明“Provider已配置”不等于外部服务一定可连接。

### 15. 为什么当前使用SQLite，而不是PostgreSQL？

SQLite是嵌入式本地数据库，不需要单独运行数据库服务，适合当前本地、单实例、低并发V1，也足以管理文档元数据和状态。PostgreSQL是成熟的独立数据库服务，更适合多人并发、多实例部署、复杂查询、权限、备份和生产可靠性。二者区别不是“计算精度”；当项目出现并发写入、多实例或复杂权限需求后，再考虑迁移。

### 16. 为什么向量放在Qdrant，而不是全部放进SQLite？

SQLite主要适合结构化数据和精确查询；Qdrant专门支持高维向量存储、余弦相似度、Top-K排序和`document_id`过滤。技术上可以把向量序列化放进SQLite，但这不等于拥有成熟高效的向量索引与检索能力。分开存储不是为了“避免混乱”，而是让组件承担各自擅长的查询模式。

### 17. 为什么V1使用Qdrant本地持久化？

本地模式部署简单、数据可持久化，并提供真实向量检索和过滤能力，符合单机作品集V1规模。它不等于最终生产架构；更大规模需要独立Qdrant服务、备份、监控、容量规划和高可用设计。

### 18. 为什么V1没有直接使用LangChain？

V1链路较短，直接定义Embedding、LLM和VectorStore接口可以减少额外依赖和隐藏行为，也便于理解每一步数据流并进行单元测试。当时对LangChain仍在系统学习，因此没有为了增加技术名词而引入无法解释的框架。未来出现复杂工作流、工具调用或多阶段编排后，可以重新评估其收益。

### 19. 为什么V1没有一次加入认证、多租户、Celery、Redis和前端？

这是范围控制和优先级管理。V1先完成最小但完整、可运行、可测试、可解释的RAG闭环。后续按触发条件增加：处理真实企业数据前优先认证和权限；文档处理时间成为瓶颈后增加异步任务；多企业使用时增加租户隔离；API稳定且普通用户需要直接操作时再增加前端。

### 20. 同步摄取有什么不足？

同一个HTTP请求必须等待文件保存、解析、切分、多批Embedding和Qdrant写入。文档越大，等待越久，可能产生请求超时、资源长时间占用和难以查询进度的问题。改进方式是上传后立即返回任务ID，由后台异步处理，并提供状态查询接口。

### 21. 当前项目还有哪些不足？

- 生产API仍使用稠密向量检索；等权BM25/RRF实验发生回退，尚无可上线的Hybrid或reranker。
- 阈值仍需更大、更真实的评估集校准。
- 歧义问题能够找回候选证据，但还没有正式的澄清响应。
- 只支持文本型PDF，没有OCR和复杂版面解析。
- 没有认证、多租户、权限隔离和正式前端。
- 本地SQLite和Qdrant适合作品集V1，不等于企业生产部署。

### 22. 下一步如何改进？

优先扩充更真实的评估集、人工检查答案并校准阈值；随后实现歧义问题的澄清响应。Hybrid不能因为技术名词热门就直接加入，必须重新设计权重或reranker并证明优于Dense。文档处理时间成为瓶颈后再引入后台任务；处理真实企业数据前增加认证、权限和租户隔离；规模扩大后再考虑PostgreSQL、独立Qdrant、监控与备份。

### 23. 你在项目中具体做了什么？

我选择将企业知识问答RAG作为个人主项目，并持续参与确定V1范围和技术边界，包括FastAPI模块化单体、TXT/PDF摄取、Chunk切分、SQLite文档记录、Qdrant向量检索、OpenAI Provider、文档范围检索、结构化引用和无证据拒答。我持续推进并验收了文档解析、检索、回答、错误处理、自动化测试、离线评估和文档整理，也完成了本地运行、接口联调和问题排查。

### 24. AI编程工具在项目中起了什么作用？

AI主要帮助分析实现方案、生成部分代码和测试、定位错误并提出优化建议。我没有把生成结果直接当作完成，而是通过范围检查、代码结构、接口操作、自动化测试和离线评估确认结果。AI可以提供选择和建议，最终是否采用、是否符合V1范围以及能否通过验收，需要由我判断。

### 25. 为什么仍然可以称为个人项目？

个人项目不等于所有代码都必须逐字符手写，更重要的是由谁对目标、取舍、集成、验证和最终结果负责。我在项目中一边学习一边推进，能够解释主要链路、技术选择、测试指标、问题排查和当前不足，也亲自完成了运行和验收。AI是开发工具，项目目标、学习过程和交付责任属于我。

## 16. 最容易答错的面试问题

1. **这是RAG模型吗？** 不是，是RAG应用；没有训练基础模型。
2. **SQLite保存正文吗？** 主要保存文档元数据和状态；原文件在uploads，Chunk和向量在Qdrant。
3. **LLM读取向量吗？** 不读取；LLM读取问题和检索到的Chunk原文。
4. **相似度0.70等于70%正确率吗？** 不等于。
5. **引用完全由LLM生成吗？** 答案编号受LLM提示影响，结构化引用元数据由应用根据真实检索结果构造。
6. **拒答能完全消除幻觉吗？** 不能，只能降低风险，需要评估和持续改进。
7. **88.20%覆盖率等于88.20%正确率吗？** 不等于，它描述测试执行过的代码分支比例。
8. **离线指标100%代表生产准确率100%吗？** 不代表，只适用于当前小规模合成语料和固定检查。
9. **`25 files skipped`表示跳过25个测试吗？** 不是，表示25个代码文件达到完整覆盖，因此未在覆盖率表中展开。
10. **PostgreSQL比SQLite精度更高吗？** 不是精度区别；PostgreSQL更适合并发、多实例、复杂权限和生产部署。
11. **Qdrant只是为了让数据不混乱吗？** 不是，主要因为它针对高维向量索引、相似度和过滤查询设计。
12. **没有LangChain只是因为不会吗？** 个人学习程度是诚实背景，但主要工程理由是V1链路短，直接接口更透明、依赖更少、更容易测试。
13. **没有企业组件只是因为做不完吗？** 应表达为范围控制：优先完成最小闭环，再由真实需求触发认证、异步任务、多租户和前端。
14. **AI辅助意味着项目不属于自己吗？** 不意味着；应诚实说明AI作用，并证明自己对范围、取舍、验收、测试和结果负责。
